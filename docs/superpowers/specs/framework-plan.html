1Goals and scope

The Selenium framework is used only as the structural reference. No feature files, tests, locators or Java code are copied.

Blank & reusableAny team clones it and adds its own application code under src/app
Same layoutfeatures → steps → pages → locators → env files → run profile → hooks
Web + API BDDGherkin for UI, REST and SOAP
Cross-browser / OS / parallelChromium, Chrome, Edge, Firefox, WebKit, mobile emulation
ReportsAllure + Cucumber + email summary
CI / CloudTeamCity now, BrowserStack with one switch
MCP + AIAuthoring, healing suggestions, failure triage (opt-in)

2Architecture: framework core vs. your code

The main rule: teams only add files in the green areas. Core finds them automatically, so nothing needs registering.

3Mapping from the Selenium framework

Every part of the Selenium framework has an equivalent here, so people already using it can be productive on day one.

The step style can match Java too. Besides When('...', fn), you can put decorators (@When('I log in as {string}')) directly on page-object methods, just like Java's @When annotations.

4Locator repository

Locators live in files, as they do today. One file per page, with keys referenced as page.key. Existing Selenium By.* syntax is accepted.

JSON (recommended): fallbacks and parameters

// src/app/locators/login.locators.json
{
  "username": "[placeholder='Username']",
  "loginBtn": [
    "role=button[name='Log in']",
    "xpath=(//*[@type='submit'])[1]"
  ],
  "rowByName": "xpath=//tr[td[text()='{0}']]"
}

.properties: Selenium style accepted

# src/app/locators/login.properties
username = By.xpath(".//input[@placeholder='Username']")
password = By.id("password")
loginBtn = By.cssSelector("button[type=submit]")
help     = By.linkText("Help")

Prefixes: css= xpath= id= text= role= testid= label= placeholder= plus By.xpath/id/cssSelector/name/linkText

How a locator key is resolved

1 · Key

"login.loginBtn" from a step or page
➜

2 · Repository

Load file, parse format, fill {0} parameters
➜

3 · Primary

Try the first locator (auto-wait)
➜

4 · Fallbacks

Try the next ones in order. Log a warning and add to the locator-health report.
➜

5 · Fail / suggest

Fail with the key and all locators tried. AI optional healing suggestion (never applied automatically)

npm run locators:check checks syntax and finds duplicate or unused keys. npm run codegen records locators for you to paste in.

5Generic step library: write tests from day one without writing code

Ready-made web and API steps work with any locator key and data reference. Custom business steps sit alongside them.

@smoke @login
Feature: Login
  Scenario: Valid user can log in
    Given I open the "login" page
    When I enter "${data.users.valid.username}" into "login.username"
    And I enter "${secret.APP_PASSWORD}" into "login.password"
    And I click "login.loginBtn"
    Then "dashboard.title" should be visible
    And I store text of "dashboard.accountNo" as "acc"
@api
Feature: Users API
  Scenario: Create user
    Given I use API "userService" with auth "bearer"
    When I send POST to "/users" with body "createUser.json"
    Then response status should be 201
    And response should match schema "user.schema.json"
    And response path "$.id" should not be empty
    And I store response path "$.id" as "userId"

Categories: navigation · click/hover · type/select/check · upload/download · frames/tabs/alerts · waits · text/attribute/count/visibility/table assertions · store & reuse values · REST · SOAP (SOAP node "Status" should be "OK"). Data references: ${data.x} ${env.X} ${secret.X} ${ctx.x} ${faker.person.firstName} ${today+2d:dd/MM/yyyy}. npm run steps:list prints the catalogue.

{
  "connection": "local",      // local|headless|browserstack|remote
  "env": "uat",
  "browsers": ["chrome","msedge","firefox","webkit"],
  "tags": "@smoke and not @wip",
  "workers": 4, "retries": 1,
  "trace": "on-first-retry", "video": "retain-on-failure"

PROFILE=crossbrowser npm test
npm test -- --tags "@login" --workers 6
npm run test:failed        # rerun last failures
npm run test:debug         # headed + inspector

9MCP and AI enhancements optional · off by default

AI helps write and maintain tests in this framework's conventions. It never changes test results silently, and a person reviews everything it produces.

#FeatureWhat it doesSwitch
A1Playwright MCP authoringThe AI explores the app in a real browser and drafts feature, locators, page and steps.mcp.json + ai/prompts/
A2Framework MCP serverLets the AI reuse existing steps and locators instead of duplicating them, validate features, run tests and read failuresai/mcp-server
A3Playwright Test AgentsPlanner / Generator / Healer agents set up for this layoutnpx playwright init-agents
A4User story → GherkinTurns acceptance criteria or a Jira story into draft features using generic stepsnpm run ai:feature
A5Locator healing suggestionsProposes a new locator after all fallbacks fail. Goes into the report or a PR patch; never applied automatically.AI_HEALING=off|suggest
A6AI failure triageGroups failures and explains the likely root cause in Allure and the emailAI_TRIAGE=on
A7Gherkin quality reviewFinds vague or duplicate steps, missing Then, and overly long scenariosnpm run ai:review-features

Guardrails: pluggable provider (AI_PROVIDER=anthropic|azure-openai|bedrock) as company policy allows. Configurable model (e.g. claude-sonnet-5-5 for cost, claude-opus-5-5 for complex generation). PII and secret redaction on DOM snapshots and logs. Token and cost caps per run. Audit log of prompts.

12Delivery phases

1 · Core skeleton

Repo, TypeScript, lint, Husky · config + run profiles · fixtures + auto-discovery · hooks · ScenarioContext · BasePage · LocatorRepository (JSON + Selenium syntax + fallbacks)
Done when: a sample web feature runs on 3 browsers in parallel

2 · Libraries

Generic step library (web + API) · RestClient · SoapClient · TestDataManager · utils · generators · steps:list · locators:check
Done when: web and API samples pass using only generic steps

3 · Reporting

Allure (+categories, history) · Cucumber HTML/JSON/JUnit · locator health · summary · email
Done when: all reports are produced and the email arrives

4 · TeamCity

Kotlin DSL · OS configurations · composite build · tabs · cache · failure conditions
Done when: composite build is green on Windows + Linux with email

5 · BrowserStack

Profile · browserstack.yml · Local tunnel through proxy · session links
Done when: samples pass on Win Chrome + macOS Safari from TeamCity

6 · AI & MCP

A1, A2, A6 first → then A4, A5, A3, A7
Done when: AI drafts a passing feature through MCP and the triage summary appears in the email

7 · Extras

E6 → E2 → E3 → E11 → E9 → E8 → rest
Done when: each one passes its own check

Throughout · Docs

README quick start · step catalogue · locator guide · "Coming from Selenium" · CONTRIBUTING
Done when: a new user runs their first test in under 10 minutes

13Risks and mitigations

RiskMitigation
Teams edit src/core and fork the frameworkLint rule + CODEOWNERS; core published as an npm package (E13)
Generic steps grow into an unmanageable keyword languageFixed, reviewed catalogue; business flows belong in custom steps and pages
AI sends sensitive data outOff by default · redaction · provider chosen by policy · audit log
AI-healed locators hide real bugsSuggestion-only; never changes test results
No macOS agentBrowserStack for macOS/Safari; WebKit on Linux until then
SMTP restrictionsConfigurable SMTP; fall back to the TeamCity notifier or a Teams webhook
